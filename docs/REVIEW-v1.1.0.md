# المراجعة الشاملة — Baraka Market v1.1.0 (ما قبل الإصدار)
تاريخ: 2026-11-01 · المراجع: المنفذ المباشر (T1→T12) · الحالة: **مشروط — صالح للإصدار بعد بندين**

## 1. الخلاصة التنفيذية

النواة مكتملة ومبرهنة: 12 مرحلة (T1→T11 + إصلاح T12) ببوابات خضراء —
**TS 266/266، Rust 14/14، `tsc` نظيف، `vite build` ناجح، توقيع المحدّث `SIG-OK`**.
البرنامج يبيع ويسوّي ويلغي ويدقق ويحدّث، بلا سحابة، بالمليم، وبتسلسل ذري.

**لكن لا تُصدر بعد.** عائقان يمنعان الـ Release:
1. **(P0 — أُصلح كودياً، بانتظار بناء)** شاشة تغيير الرمز الإجباري كانت ميتة في الـ `.exe` (أمر `change_pin` الأصلي لم يكن موجوداً أصلاً). الإصلاح + اختباره أخضر، لكن مثبت `1.1.0` الحالي في `releases/` بُني **قبله** — أي نسخة تُنشر منه تحمل الخلل. يلزم **إعادة بناء** قبل أي Release.
2. **(قرار مالك)** المستودع **خاص** (تم التحقق: `private: true`)، بينما صُمم T9 على أنه عام (تحميل مجهول لـ `latest.json` + المثبت). القرار: مستودع إصدارات عام منفصل أم USB فقط؟ (التفصيل في §5).

## 2. المنهجية

مراجعة منفذ-مراجع مزدوجة: كل مرحلة سُلّمت بـ TDD (أحمر→أخضر حقيقي — سُجّلت حالات اصطاد فيها الأحمر عيوباً فعلية)، ثم `lint + test:all + build + cargo test` كبوابة التزام، ثم ADR + توثيق + `commit + push`. هذه المراجعة أضافت: فحص المسارات الحرجة يدوياً (الدخول، التغيير الإجباري، الـ lanes الأصلية)، مطابقة العقود (`invoke` ↔ `generate_handler` ↔ الاختبارات)، وإعادة تشغيل البوابات الأربع طازجة.

## 4. الملاحظات (مرتبة بالخطورة)

- **P0 — الدخول (مُصلح، بانتظار بناء):** `change_pin` الأصلي كان مفقوداً → تغيير الرمز الإجباري مستحيل في الـ exe → المالك محجوب. السبب الجذري: T8 سلّم `verify/list` وأجّل `change` لـ "T8b" لم تُنجز، والتعليق في الكود اعترف بذلك. الإصلاح: `auth.rs::user_change_pin` + أمر `change_pin` + اختبار. **القاعدة المستفادة:** أي `invoke` بلا أمر مسجل يجب أن يُسقط الـ build — أُضيف فحص يدوي لقائمة الـ handler في T12 close-out.
- **P1 — T9 على مستودع خاص:** التصميم الحالي (feed عام مجهول) لا يعمل مع `private: true`. الخيارات في §6.
- **P2 — مثبت `1.1.0` الحالي قديم:** بُني قبل إصلاح P0 — لا يُنشر أبداً، يُعاد بناؤه.
- **P3 — تجميل مؤجل (معروف):** عيوب T3 البصرية (typos/truncation) + `8h soak` الميداني + E2E المحدّث حياً — كلها مسجلة كخطوات T12 exit، ليست مفاجآت.

## 5. أثر "خاص لا عام" على T9 (تحليل دقيق)

المستودع خاص = `releases/latest/download/*` تتطلب مصادقة = المحدّث الصامت **يفشل بصمت** على كل محل (الكاشير يرى "لا تحديثات" وهي كذبة). البدائل:

| الخيار | الكلفة | الأمان | التوصية |
|---|---|---|---|
| **A. مستودع إصدارات عام منفصل** (`BarakaMarket-releases`: فقط `latest.json` + `.exe` + `.sig`) | إنشاء repo + تغيير سطر endpoint واحد + إعادة بناء | ممتاز (لا أسرار على المحلات، الكود يبقى خاصاً) | **موصى به** |
| B. USB/يدوي فقط (تعطيل الفحص التلقائي) | صفر تقني | ممتاز | احتياط مقبول إن رفضت أي عام |
| C. توكن قراءة على المحلات | سطر واحد لكن **سرّ مسرّب على كل till** + دوران مؤلم | سيئ | مرفوض |

ملاحظة: التوقيع ed25519 يبقى صالحاً أياً كان الخيار — الثقة بالمفتاح لا بالقناة.

## 6. المتبقي (مرتب، لا يُتجاوز الترتيب)

1. **قرارك:** A أم B للمنفذ الخاص؟ (سؤال واحد أدناه).
2. إعادة بناء `1.1.0` (بعد القرار — الـ endpoint قد يتغير) + `SIG-OK` + دخان تثبيت نظيف.
3. `latest.json` + `gh release create v1.1.0` + وسم + دفع.
4. E2E الدخول حياً على المثبت الجديد (`owner` → تغيير إجباري → POS) — إثبات إغلاق P0.
5. `commit + push` الختامي (T12 close-out + ADR-036).

## 7. المخاطر المتبقية

- فقدان `.secrets/baraka-updater.key` = موت كل تحديث قادم (انسخه إلى USB — ما زال مطلوباً).
- أي `git add` للمفتاح = كارثة (المستودع خاص لكن الأسرار لا تدخل git أبداً) — الحماية: `.gitignore` + تحقق `check-ignore` في كل T.
- الكاشير لا يثبّت أبداً أثناء الدوام (التثبيت للمدير/المالك + الزر محجوب عن الكاشير) — مطبّق في `UpdateManagerView`.
