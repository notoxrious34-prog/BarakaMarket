# التدقيق العميق الثاني — Baraka Market v1.1.0 (وظيفي، مُنجز حياً)
تاريخ: 2026-11-01 · المنهج: إتمام التدفقات لا مشاهدتها (بيع نقدي كامل 660/1000/340 حتى التذكرة + فحص DB بعده: `sales_count: 0`!)، مطابقة كل ادعاء مع الكود أو قاعدة البيانات. الحكم: **3 عيوب حقيقية (واحد P1)، + تأكيد 5، + تبرئة 2. والحزمة S مرفوضة بحق — تُستبدل بما أدناه.**

## رأي صريح (محدّث بعد الإنجاز الحي)
البرنامج يبيع ويحسب صرفه صحيحاً (340 ✓) والتذكرة صادقة في رقمها (`DRAFT-T-…`)، لكن لحظة الحقيقة صامتة عن الفشل: لا فرق مرئي بين "طُبع كمسودة" و"رُحّل جبائياً" — بيع كامل انتهى بـ `sales_count: 0` بلا أي تحذير. والخادم الذي يفترض أن يتقبل أي قاعدة قديمة يسقط على أقدم ملف عندنا (`no such column: day`). هذان هما الدين الحقيقي — الباقي تجميل. الكاشير المتمرس سيتأقلم؛ الكاشير الجديد سيخطئ.

## العيوب (مرتبة — بعد الإنجاز الحي)
**P1 — مسار المتصفح: بيع "ناجح" لا يُحفظ أبداً، بلا أي إشارة (مُبرهن: `sales_count: 0` بعد تأكيد حي 660/1000/340).** `getLoopbackToken()` تُرجع `null` خارج Tauri → POST بلا ترويسة → `401` → الـ commit يُصفَّر في `baraka_sale_outbox_v1` بصمت والسلة تُمسح والتذكرة تُطبع `DRAFT-`. لا شارة "غير مرسل". (الـ `.exe` سليم؛ الخطر على المتصفح/الدعم/التجريب.)
**P1 — الخادم يموت على القاعدة الذهبية (مُبرهن: crash + stack).** `no such column: day` في `sqlite.ts:408` — `db.exec(schemaSql())` يطبق `idx_z_day` قبل أي ترحيل والملف الذهبي أقدم من العمود. (مخفف: أول إصدار؛ لكن v1.2 سيصطدم.)
**P1 — نسخة كاذبة (مُبرهنة كوداً وورقياً):** `App.tsx:104` ثابت `v1.0.1` والحزمة `1.1.0`؛ والتذكرة تذيّل `Baraka Market v1.0 by BarakaDEV`. سطر + قالب.
**P2:**
1. تقطع الشريط العلوي: `إغلاق`→"اغا"، `Rapport :` بنقطتين، تبويبات الأقسام مقطوعة، شارة الجلسة مبتورة — يتمدد سوءاً على 1366.
2. الطابع `min 10 DA` غير مفصح: فاتورة 650 تدفع طابع 10 (الـ 1% = 6.5 يُرفع للحد الأدنى). السلوك مقصود (`timbre_min=10`) لكن لا سطر يشرحه للكاشير/الزبون — **يُعتمد الحد مع محاسبك أو يُخفض**.
3. الديون: زبون مدين 4500 مع صندوقي "لا مشتريات/لا دفعات" فارغين — تناقض يفقد الثقة؛ حذف زبون مدين بلا تحذير؛ زر الإضافة أحمر (لغة الحذف)؛ زبون برصيد 0 يُحسب ضمن "3 زبائن".
4. السلة: `x 650 DZD 1` (bidi)، `+` يساراً (معكوس RTL)، لا إدخال كمية مباشر (12 قارورة = 11 نقرة)، سطور `+0.00` ضجيج، زر الحذف ملاصق للسعر بلا تراجع.
5. الإغلاق: صفحة "إغلاق" تعرض "فتح" عند غياب الجلسة (التباس)، والتدفق المنتظر (متوقع/معدود/فرق + سبب + تأكيد) غير مرئي — نمط النقرة الواحدة على المال مرفوض.
6. الإعدادات: لا زر حفظ ظاهر في الشاشة (autosave؟ ضياع؟)، بيانات مرة-بالعمر + عمليات يومية + خطر في تمريرة واحدة، والمعرفات قابلة للتحرير بعد بدء الفوترة.
**P3:**

9. الرخصة: الـ HWID تحت الطيّة (خطوة التفعيل الأولى مخفية)، لا زر نسخ.
10. النهاري: أسعار خضراء على أبيض ~2.5:1، سطر الطابع يختفي، `DATE COURTE` أسود-على-أحمر، حبوب سوداء دخيلة (`Space Paiement Rapide`)، شارة `owner` غير مقروءة.

## المقترحات (تُستبدل S المرفوضة — بالترتيب)
1. **شارة الطابور + ختم "غير مُرحّلة"** (P1 المتصفح): عدّاد مرئي + زر إعادة + ختم على المطبوع قبل المزامنة.
2. **إصلاح إقلاع المخطط القديم** (P1 الخادم): فصل الفهارس/triggers عن إنشاء الجداول (بعد الترحيل) + اختبار `golden-legacy` يُسقط البناء عند الانتكاس.
3. **النسخة + التذييل + الإفصاح عن حد الطابع** (P2، ساعات) — ثم حزمة S القديمة كما هي أدناه.
## مقترحات S/M/L السابقة (تبقى كما هي)
- **S (ساعات):** إصلاح النسخة + الأخطاء اللغوية + `fruits_legumes` + زر نسخ HWID + إظهار "الحد الأدنى 10 دج" بجانب الطابع + إخفاء سطور `+0.00` + زر إضافة أخضر + إخفاء رصيد-0 من العدّاد.
- **M (أيام):** تباين النهاري (أخضر داكن، نصوص رمادية أغمق، شارات معاد تلوينها) + إدخال كمية مباشر + تأكيد حذف الزبون المدين + تأكيد الإغلاق المزدوج (متوقع/معدود/فرق) + تقسيم الإعدادات لتبويبات (جبائية/محل/مستخدمون/نسخ/خطر) مع حفظ صريح + منع تحرير NIF بعد أول فاتورة إلا بصلاحية مالك وتدقيق.
- **L (إصدار):** لوحة مفاتيح لمسية في الدفع + دفتر ديون بجدول (تاريخ/فاتورة/مدفوع/متبقٍّ) + حدود سقف مع شريط استهلاك + تنبيهات انتهاء داخل الشاشة + اختصارات قابلة للتخصيص.

ملاحظة أمانة: "SOLITE/SQUITE WAL" التي ظهرت في التحليل هي خطأ قراءة آلية لـ **SQLITE WAL** — ليست عيباً.
